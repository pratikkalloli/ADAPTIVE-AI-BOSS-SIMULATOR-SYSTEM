# Telemetry lifecycle verification

## Findings

The Stage 2B.2 terminal guard is already present in `Assets/Scripts/DataLogger.cs`; no gameplay code change was needed for this review. `LogEpisodeEnd` returns when the episode is already ended, writes one `EpisodeEnd` row with `terminated=true` and the supplied outcome/HP values, then marks the logger ended. All telemetry helpers funnel through `WriteEvent`, which rejects later calls. Unity animation callbacks and coroutines therefore use the same guard when they emit telemetry after death.

`KnightScene.unity` contains one active, ordinary scene `DataLogger` object. On reload, `DataLogger.OnDestroy` clears its singleton, while the next instance's `Awake` generates a GUID and reserves a new `combat_logs_v2_<episode-id>.csv` using `FileMode.CreateNew`. `CombatManager` ends the episode after applying the final HP update and selecting `player_win` for boss death or `boss_win` for player death. Scene restart uses `LoadSceneMode.Single`.

- `combat_logs_v2_b3e9186c77b1413d82a8c98a1da48268.csv`
- `combat_logs_v2_9d79399181474de9b71644896093c5df.csv`

Each of the six inspected files had exactly 33 fields on every parsed row, one start, one terminal event, and a single episode ID. The four later files are existing runtime evidence, not logs generated by this review. They indicate the guard is effective in those runs; Unity Play Mode was not run as part of this review.

## Verification and remaining limits

- Source inspection confirmed all current telemetry emitters reach the central guarded writer.
- CSV inspection confirmed the 33-field schema, episode IDs, counts and terminal-row positions above.
- `git diff --check` was run; see the task summary for its result.
- No Unity compilation or Play Mode test was run. For an additional manual check, start `KnightScene`, complete a fight, confirm exactly one start/end and no later rows, then press `R` to reload and repeat. Confirm the second run has a different episode ID and a new file.

This verifies the checked logs and sequential Unity callback lifecycle. It does not establish behavior for hypothetical telemetry writes from background threads; the project's inspected emitters are Unity callbacks/coroutines and use the main thread.
